## Context

Dockge 当前的远程 Agent 方案接收任意 URL、用户名和密码，将密码以 JSON 写入 bbolt，并由中心实例登录远端、缓存令牌、代理 compose 栈读写和生命周期操作。这使中心实例成为跨主机 Docker 控制平面。当前方案没有设备身份、mTLS、目标 allowlist、凭据加密或细粒度授权。

## Goals / Non-Goals

**Goals:**
- 将运行时管理范围限制为 Dockge 实例所在主机。
- 移除保存和使用其他主机登录凭据的后端路径。
- 保持本地栈、容器、镜像、网络、卷、终端和设置功能不变。
- 保留既有 bbolt 数据库的可打开性，不以数据删除作为升级前提。

**Non-Goals:**
- 不实现新的多机控制平面、mTLS、VPN 编排或外部身份提供商。
- 不删除已有数据库内遗留的 `agents` bucket。
- 不在本变更中改造前端 Agent 页面或视觉布局。

## Decisions

- **单机为产品边界**：Dockge SHALL 只管理部署实例所在主机的 Docker 或 Podman 运行时。管理员可以从远程浏览器访问该实例，但该实例不得连接、保存凭据或代理操作至另一台主机。
- **删除而非加固半成品多机方案**：多机能力需要独立的信任与设备生命周期设计，不能通过 URL 校验或凭据加密补丁安全地完成；当前产品没有该需求，因此删除其后端实现。
- **旧数据惰性保留**：bbolt 没有安全且通用的在线 bucket 删除需求。升级后代码不创建、不读取、不写入 `agents` bucket；管理员可按既有运维流程处置旧数据库备份。
- **前后端分步收敛**：本变更先关闭可利用的后端控制面。前端残留入口不再能调用有效 API，但其删除属于单独的 UI 变更，避免超出本次后端范围。

## Risks / Trade-offs

- 已依赖 Agent API 的外部客户端会收到 404；这是有意的破坏性 API 删除。
- 现有数据库中的 Agent 凭据不会被本次代码自动抹除。运营者如需立即清除，应在完成备份策略评估后重建或离线处理数据库。
- 前端在后续清理前仍可能展示失效入口；这不会恢复跨主机控制能力。
